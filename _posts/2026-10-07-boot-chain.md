Итак, старый добрый Т480 стоит на моем столе. Libreboot перепрошит. Первоначальная установка завершена, и я готов нажать кнопку питания.

Запуск.

И через полминуты я вижу приглашение консоли `login:`. 
Но что только что произошло? Как загрузилась система? Где живёт каждый конфиг, который влияет на загрузку, и кто его читает?

Эта статья - заметка про путь, который проходит система от старта, до загрузки через **legacy BIOS** на диске с **GPT**, полным шифрованием **GELI** и корнем на **ZFS**. Т.е. то, что ставит `bsdinstall`, если выбрать «Auto (ZFS)» с шифрованием на машине без UEFI. 
С UEFI в моем конкретном случае все сложно, так что рассмотрю вариант через legacy BIOS

> **Почему BIOS, а не UEFI на Libreboot**
>
> На машинах с coreboot/Libreboot прошивка состоит из двух слоёв. Coreboot только инициализирует железо: память, процессор, шины. А то, что видит операционная система, даёт второй слой - **payload**. SeaBIOS отдаёт классический BIOS, GRUB грузит систему сам, UEFI-payload отдаёт UEFI. Какой «BIOS» видит FreeBSD, решает не ноутбук, а выбранный payload.
>
> Для BSD документация Libreboot предполагает SeaBIOS: грузить BSD через GRUB технически можно, но не советуют. Рабочий и документированный путь для FreeBSD на момент написания - SeaBIOS в режиме `txtmode`.

## Шифрование диска

Весь диск зашифрован. Ядро лежит внутри зашифрованного ZFS-пула.

Значит, ядро не может само себя расшифровать, его надо сначала **найти**, а для этого кто-то должен расшифровать диск и прочитать ZFS **до** ядра. 
Естественно тот, кто расшифровывает, сам зашифрован быть не может.

Отсюда вся конструкция: на диске есть маленький **открытый** кусок, который умеет ровно столько, чтобы спросить пароль и добраться до остального.

## We need go deeper

Вот так выглядит схема (в общем виде) этапов загрузки:

```
  кнопка питания
  │
┌─▼────────────────────┐
│ BIOS (SeaBIOS)       │   читает 1 сектор (512 байт) — и всё
└─┬────────────────────┘
┌─▼────────────────────┐
│ сектор 0: pmbr       │   защитный MBR: ищет в GPT freebsd-boot
└─┬────────────────────┘
┌─▼────────────────────┐
│ раздел freebsd-boot  │   ~512 КБ, единственный открытый код
│ gptzfsboot           │   понимает GPT + GELI + ZFS
│ → спрашивает пароль  │──┐ ключ
└─┬────────────────────┘  │
══╪════════════════════════╪═══ выше открыто ▲ ▼ ниже внутри GELI
┌─▼────────────────────┐  │
│ /boot/loader         │◄─┤ меню, loader.conf,
│                      │  │ ядро + модули (zfs, geom_eli)
└─┬────────────────────┘  │
┌─▼────────────────────┐  │
│ ядро                 │◄─┘ открывает GELI готовым ключом,
│                      │    монтирует корень из bootfs
└─┬────────────────────┘
┌─▼────────────────────┐
│ init → rc → rc.d/*   │   rc.conf, sysctl.conf, сервисы
└─┬────────────────────┘
  ▼
  login:
```

Я иду по шагам.

### 1. BIOS и "нулевой сектор"

BIOS ничего не знает ни про FreeBSD, ни про GPT, ни тем более про шифрование. Он умеет одно ровно одно - прочитать первый сектор диска и передать туда управление.

В этом секторе лежит `pmbr` (protective MBR). Он «защитный», потому что для старых программ выглядит как обычный MBR с одним разделом на весь диск и они не трогают GPT. Но внутри у него ещё и крошечный код для того чтобы найти в GPT раздел типа `freebsd-boot` и загрузить его.

### 2. Раздел freebsd-boot и gptzfsboot

```
# gpart show
=>       40  500118112  nda0  GPT  (238G)
         40       1024     1  freebsd-boot  (512K)
       1064        984        - free -  (492K)
       2048    4194304     2  freebsd-swap  (2.0G)
    4196352  495920128     3  freebsd-zfs  (236G)
    ...
```

Первая строка - это он: полмегабайта открытого кода. Внутри маленький `gptzfsboot`, это первая программа в цепочке, которая знает про GELI и ZFS.

Откуда она знает, что раздел зашифрован и надо спрашивать пароль? Из метаданных GELI на самом разделе:

```
# geli list | grep -i flags
Flags: BOOT
```

Флаг `BOOT` ставится при создании шифрования (`geli init -b ...`, инсталлятор делает это сам). Он означает буквально «спроси пароль на этапе загрузки». Нет флага - gptzfsboot не будет ничего спрашивать и раздел не откроет.

Пароль введён - gptzfsboot расшифровывает раздел, находит ZFS-пул и читает из него следующую ступеньку.

### 3. /boot/loader

Это уже не крошечный код, а полноценный загрузчик с меню (на Lua). Он живёт **внутри** пула, рядом с ядром.

Что он делает:

1. читает свои конфиги: сначала `/boot/defaults/loader.conf` (умолчания, руками не трогаем), потом `/boot/loader.conf` (наши правки);
2. загружает в память ядро `/boot/kernel/kernel` и модули, которые попросили в конфиге;
3. выясняет, какой dataset монтировать как корень, и кладёт это ядру в переменные окружения.

Для шифрованного ZFS-корня в `loader.conf` обычно есть:

```
zfs_load="YES"        # модуль ZFS - без него ядро не поймёт, что лежит на диске
geom_eli_load="YES"   # модуль GELI - без него ядро не откроет диск
aesni_load="YES"      # аппаратное ускорение AES (на новых версиях может быть уже в ядре)
```

Я обратил внимание на то, что загрузчик сам ZFS читать умеет, иначе он не нашёл бы ни себя, ни ядро. Но ядру нужен свой модуль. Это две разные реализации на двух разных ступеньках.

Какой корень монтировать, берётся из свойства пула `bootfs`:

```
# zpool get bootfs zroot
NAME   PROPERTY  VALUE               SOURCE
zroot  bootfs    zroot/ROOT/default  local
```

Это свойство ещё вернётся в статье про ZFS: на нём построены boot environments - несколько корней в одном пуле и выбор, с какого грузиться (одна из самых "сладких" особенностей FreeBSD).

### 4. Один пароль - один ввод

Ядру тоже нужен ключ: оно само будет работать с зашифрованным диском дальше. Но второй раз пароль никто не спрашивает.
Потому что ключ передаётся по цепочке: gptzfsboot отдаёт его loader'у, loader кладёт его в специальную область памяти вместе с ядром, и ядро при старте забирает его оттуда.

### 5. THE CORE

Ядро просыпается, находит устройства, подключает GELI готовым ключом и монтирует корень. Что именно монтировать, оно смотрит в переменной, которую оставил loader:

```
# kenv vfs.root.mountfrom
zfs:zroot/ROOT/default
```

Корень смонтирован - ядро запускает первый процесс, `/sbin/init`.

### 6. init и rc. Или где живут сервисы

`init` (PID 1) запускает shell-скрипт `/etc/rc`, и начинается обычная жизнь системы:

1. `rc` читает `/etc/defaults/rc.conf` (умолчания) и потом `/etc/rc.conf` (мои правки будут тут);
2. по зависимостям (`rcorder`) запускает скрипты из `/etc/rc.d/` и `/usr/local/etc/rc.d/` - сеть, файловые системы, демоны;
3. один из этих скриптов применяет `/etc/sysctl.conf`;
4. в конце `init` запускает `getty` на консолях - и я вижу `login:`.

## Карта: какой конфиг кто читает и когда


| Файл | Кто читает | Когда | Что туда кладут |
|---|---|---|---|
| `/boot/loader.conf` | loader | до ядра | модули ядра, tunables (то, что можно задать только до старта ядра) |
| свойство `bootfs` пула | loader | до ядра | какой dataset станет корнем |
| `/etc/sysctl.conf` | rc (скрипт `sysctl`) | после ядра, при загрузке | параметры ядра, которые можно менять на лету |
| `/etc/rc.conf` | rc | после ядра, при загрузке | какие сервисы запускать и с какими настройками; сеть |
| `/etc/rc.d/*`, `/usr/local/etc/rc.d/*` | rc | после ядра, при загрузке | сами скрипты сервисов (базовой системы и из пакетов) |

Простое правило, чтобы не путать `loader.conf` и `sysctl.conf`: если параметр нужен ядру **в момент старта** (загрузить модуль, выделить память) - это `loader.conf`. Если его можно поменять командой `sysctl` на работающей системе - это `sysctl.conf`.

И общее правило для всех: `/boot/defaults/...` и `/etc/defaults/...`: их править смысла нет, потому что их перезапишет первое же обновление. Мои правки в файлах без `defaults`, они перекрывает умолчания.

## Проверить поверхность

```
gpart show                         # есть ли раздел freebsd-boot
geli list | grep -i flags          # стоит ли флаг BOOT
cat /boot/loader.conf              # какие модули грузятся до ядра
zpool get bootfs                   # какой корень выбран
kenv vfs.root.mountfrom            # что loader передал ядру
```

Если всё совпало со схемой выше - значит, я только что прошёл всю цепочку загрузки.

## Когда цепочка рвётся: на какой я ступеньке?

Схема выше нужна не только для понимания. Когда загрузка ломается, первый вопрос - **до какой ступеньки я дошел?**. Это видно по тому, что на экране:

| На экране | Ступенька | Что это значит |
|---|---|---|
| пусто сразу после BIOS | прошивка / pmbr | до кода FreeBSD не дошли |
| `boot:` | gptzfsboot | пароль принят, но loader не найден или не прочитан |
| `OK` | loader | ручное управление загрузчиком (`Esc` из меню) |
| `mountroot>` | ядро | ядро запустилось, но не смогло смонтировать корень |
| `Enter full pathname of shell` | init | однопользовательский режим, корень пока только для чтения |

И сразу правило: всё, что выше сломавшейся ступеньки, работает. Пароль GELI приняли - значит, pmbr, gptzfsboot и шифрование в порядке, искать надо дальше.

### Пример: сломанная строка в loader.conf

После правки `/boot/loader.conf` система грузится так: пароль GELI принят, меню показалось, ядро стартует, но всё заканчивается на `mountroot>`. Попытка вручную указать корень даёт:

```
mountroot> zfs:zroot/ROOT/default
error 2: unknown file system
```

Читаю по ступенькам:

- пароль принят → gptzfsboot и GELI в порядке;
- `mountroot>` → ядро живо, корень не смонтирован;
- `unknown file system` → ядро **не знает ZFS**, то есть модуль `zfs.ko` не загружен.

Модули загружает loader по списку из `loader.conf`. Если в файле синтаксическая ошибка, например, незакрытая кавычка, строки ниже неё могут просто не примениться, и `zfs_load="YES"` до ядра не доходит.

Из `mountroot>` модуль уже не загрузить, это работа предыдущей ступеньки. Поэтому возвращаемся на неё:

```
Ctrl+Alt+Del                  # перезагрузка, снова пароль GELI
                              # в меню - Esc, появится OK
OK load zfs                   # загрузить модуль ZFS вручную
OK boot -s                    # загрузиться в однопользовательском режиме
```

В однопользовательском режиме корень смонтирован только для чтения, поэтому сначала:

```
# mount -uw /
# ee /boot/loader.conf        # исправить строку, сохранить
# reboot
```

### Две ручки для диагностики

Если загрузка «висит» без сообщений, я включаю подробный вывод. В приглашении `OK`:

```
OK set boot_mute=NO           # не прятать сообщения ядра
OK boot -v                    # загрузиться с подробным выводом
```

Последняя строка перед зависанием обычно и подсказывает, какая ступенька споткнулась.

### Последний рубеж: флешка

Если не получается добраться даже до `OK`, всегда можно загрузиться с установочной флешки FreeBSD (Live System) и открыть диск руками:

```
# geli attach /dev/<раздел>               # спросит пароль, появится <раздел>.eli
# zpool import -N -R /mnt zroot           # импорт пула без монтирования
# zfs mount zroot/ROOT/default            # корень окажется в /mnt
```

Теперь `/mnt/boot/loader.conf` можно поправить, как обычный файл.

### Профилактика

Правки в `loader.conf` не редактором, а через `sysrc`:

```
# sysrc -f /boot/loader.conf zfs_load=YES
```

`sysrc` сам расставит кавычки и не оставит незакрытую. А перед рискованной правкой я вообще делаю `bectl create <имя>`: `/boot` лежит внутри boot environment, и старую версию файла можно будет выбрать прямо в меню загрузчика.
